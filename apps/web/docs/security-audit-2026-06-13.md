# NoteMage Security Audit — Cost-Bankruptcy & Access Control
**Date:** 2026-06-13
**Scope:** Full `apps/web` codebase (196 API routes, AI-call sites, auth, billing, infra). Self-hosted on Coolify (no edge WAF/DDoS), Supabase Postgres via Prisma.

## Method
Fresh, ground-up audit by **39 Opus 4.8 agents** (no Fable agents), orchestrated as a workflow:
- **6 parallel finders**, one per dimension: AI cost-runaway, rate-limiting/DoS/brute-force, AuthZ/IDOR/RLS, auth/secrets/webhooks, injection/SSRF/RCE, billing-integrity/data-exposure.
- **Adversarial verification:** every finding was handed to a *separate* skeptical Opus agent that re-opened the exact cited file+lines, confirmed the quoted code exists, and hunted for mitigating controls the finder missed. Verdict per finding: confirmed / refuted / needs-info.
- Finders were **barred from reading any prior audit doc** — every finding derives from current source.

**Verification result: 32 confirmed, 0 needs-info, 0 refuted/hallucinated.**

## Lead spot-checks (direct code read, post-workflow)
The headline bankruptcy claims were re-verified by hand against the source:
- ✅ **Token budget is blind to the costliest routes.** `recordTokenUsage()` (token-budget.ts:44-60) has only **3 callers** — essay-check, ai-inline, summarize. Path generation, page-generate, PDF/video import, moderation, chat-title/intent and classify never record into it, and `checkTokenBudget` sums `ChatMessage.tokens` only (token-budget.ts:31-37). So the "monthly hard ceiling" cannot be tripped by path-gen or imports. *Nuance:* chat + essay/inline/summarize **are** self-limited by it; path **creation** is separately metered by the `ai_study_plan`/`ultra_path` credit (FREE=0 when cutoff on → blocked; **PRO=-1 → unlimited**).
- ✅ **Rate limiter fails open.** `rateLimit()` defaults `failClosed=false` and returns success on any Redis error (rate-limit.ts:56-67); `getRedis()` throws if `UPSTASH_*` is unset (redis.ts:8-12). Auth routes correctly opt into `failClosed=true`; AI/cost routes do not → during a Redis outage (or if Redis is unconfigured) the only app-layer throttle on paid AI vanishes.
- ✅ **No global throttle.** middleware.ts:164-174 enforces a uniform auth gate (401) on all /api routes but applies **no** rate limiting. Anonymous flooding of authed routes is cheaply rejected; authenticated flooding and public-route (waitlist/currency/telemetry/auth) flooding is not.
- ✅ **PDF-import retry** (retry/route.ts) has no rate limit and no meter; idempotency stops double-firing a *live* job but a reliably-failing job can be re-queued in a loop.
- ✅ **regenerate** consumes no `ai_study_plan` credit (by design) and leans on the 10/min limiter (fail-open) + the ineffective token budget.
- ⚠️ **RLS:** 0 policy statements across all 80 migrations (confirmed). Whether RLS is *enabled* and what DB role Prisma connects as live in `DATABASE_URL` (not in repo) — **verify this in the Supabase dashboard.** If RLS is off + a privileged role, the (uniformly-correct) app-layer ownership checks are the *only* tenant isolation.

## Executive summary

The single worst scenario is a **runaway AI bill via path generation**: the monthly token budget (`checkTokenBudget`) — which the code itself documents as the "hard ceiling" that "caps the COGS" so a PRO user "could [not] generate unbounded paths" — is **blind to every expensive non-chat AI route**. It sums only `ChatMessage.tokens`, but path generation, PDF/video import, moderation, and the classifier all record spend to a separate `aiUsageEvent` table that is never read as a quota gate. The `/regenerate` and `/translate` path routes rely on that ceiling as their *only* COGS backstop and consume no per-feature meter at all, leaving them capped only by a 10/min rate limiter — which itself **fails open** if Redis is unreachable. A single scripted authenticated account can therefore drive uncapped Anthropic/Gemini path generation; even with idempotency narrowing the worst case, this is a four-to-five-figure monthly exposure that scales linearly across accounts and has no automated cost alert in code.

Two more bankruptcy vectors compound it: the **PDF-import retry route** (no rate limit, no budget check, success-only metering) lets a crafted reliably-failing PDF be re-run in a loop, re-firing per-page vision LLM calls for free (~$360–$1,800/hr/account); and the **path-publish loop** (no rate limit, no meter) re-runs Gemini L2 + Sonnet L3 moderation on every publish→unpublish→republish cycle, with the P13 trust gate routing every fresh account to the expensive L3 on essentially every cycle. There is **no free-PRO / tier-escalation vector** — billing webhooks, the self-serve tier endpoint, and credential/OAuth flows are all solid. On the data side, app-layer ownership checks are uniformly correct, but **RLS is entirely absent** and Prisma connects as the privileged `postgres` role, so a single future forgotten `userId` constraint becomes immediate full cross-tenant exposure with no DB safety net. The deployment is self-hosted Coolify with **no edge WAF**, so all of these app-layer gaps are the only defense — including the lack of any global per-IP throttle, which leaves all 196 routes floodable.

## All confirmed findings by severity

### Critical

**`checkTokenBudget` is blind to the most expensive AI routes** — `src/lib/token-budget.ts:31-37`
The single per-tier monthly "hard ceiling" (FREE 100k, PRO 1M tokens) computes used tokens *only* by aggregating `ChatMessage.tokens`. Only chat, ai-inline, essay-check, and doc-summarize write through that path. Path generation Stage B (`path-generator.ts:229-242,555,2397`), pdf-import (`run-job.ts:309`), video-import (`gemini-ingest.ts:367`), chat-intent (`chat-intent.ts:139`), the classifier (`path-classifier.ts:121,146`), image-captions, and chat-title all record exclusively to the `aiUsageEvent` table, which is **enforcement-dead** — read in exactly one place (`app/api/admin/stats/route.ts`) for the admin dashboard, never as a quota gate. Routes that name this budget as their only COGS guard (`paths/route.ts:139-141`, `regenerate/route.ts:31-34`) self-document the gap; both backstops are no-ops for path tokens.
*Attack:* A PRO user scripts `POST /api/learn/paths/[planId]/regenerate` at the 10/min rate limit (or fires up to 10 distinct-plan regenerations/min, plus unlimited fresh PRO path creation since `ai_study_plan=-1`). `checkTokenBudget` always returns `allowed=true` regardless of how many full multi-slot Stage-B generations have run. Sustained four-to-five-figure monthly spend per account, horizontally parallelizable.
*Fix:* Switch `checkTokenBudget` to aggregate `AiUsageEvent.inputTokens+outputTokens` (already captures every surface), or have every non-chat surface write its token total to the same ledger `checkTokenBudget` reads. Additionally cap regenerate/translate with their own monthly meters.

### High

**PDF-import retry has no rate limit and no budget check; failed jobs never meter** — `app/api/notebooks/[id]/pdf-import/[jobId]/retry/route.ts:25-76`
Between the ownership check (`:32-36`) and `void runPdfImportJob(jobId)` (`:72`) there is no `rateLimit`, no `checkUsageLimit`, no `checkTokenBudget` (verified by grep). The original POST has both (`route.ts:106`, `:191-199`); the retry imports neither. Metering is success-only (`run-job.ts:533`, just before `succeeded=true` at `:537`), and temp uploads persist on failure, so a job that fails *after* the page loop but before `:537` (e.g. `db.page.create` at `:429`, figure upload `:448-468`, `assembleTiptap` at `:471`) burns the full vision spend and meters zero.
*Attack:* A FREE user (50-page lifetime allowance) uploads a near-50-page PDF crafted to fail late, then scripts the retry in a tight loop. Each retry re-runs up to 50 Gemini (and, with `PDF_TABLE_ESCALATE=1`, Sonnet) vision calls — ~$360–$1,800/hr/account, none metered while it keeps failing.
*Fix:* Add a per-user rate limit + `checkUsageLimit('pdf_import')` pre-check mirroring the POST; meter pages actually processed even on failure, or charge a reserve up front and refund only successfully-imported pages.

**Path-publish has no rate limit and no meter; republish re-runs L2 (Gemini) + L3 (Sonnet)** — `app/api/learn/paths/[planId]/publish/route.ts:72-103`
The handler has no `rateLimit` and no usage meter (verified against imports `:32-46`). L1 is a pure synchronous wordlist filter (zero AI cost — *corrects the finding's "L1→L2→L3" framing*), but it fires `runLayer2` (`layer2-runner.ts:134`, Gemini 2.5 Flash) and, on `auditing_l3`, `runLayer3` (`:323-325`, Anthropic Sonnet via `AI_GENERATION_MODEL`). The idempotency guard keys only on an existing `SharedPath` row; DELETE removes it (`community/paths/[shareId]/route.ts:~722`), so publish→unpublish→publish creates a fresh row and re-runs the chain. The P13 trust gate (`applyTrustGate`, `layer2-runner.ts:177-187`) **downgrades a clean L2 pass to `auditing_l3` for any untrusted non-admin author**, so a fresh-account attacker routes to expensive Sonnet L3 on essentially *every* cycle.
*Attack:* Scripted publish→DELETE→publish loop; each cycle costs ~1 Gemini Flash L2 + ~1 Sonnet L3 call, all unmetered and invisible to `checkTokenBudget`. ~$36–$360/hr/account in L3 spend.
*Fix:* Per-user rate limit + a `moderation_audit` meter; retain a cost record keyed to (userId, planId) and refuse to re-moderate identical content within a window.

**`regenerate` and `translate` consume NO usage credit** — `app/api/learn/paths/[planId]/regenerate/route.ts:31-48` (translate: `…/translate/route.ts:33-46`)
Both deliberately skip `incrementUsage` (their own comments confirm); their only guards are a 10/min rate limit + `checkTokenBudget`, which (per the critical finding) never sees path tokens. The conditional `updateMany` claim (`:67-84`) only blocks a concurrent live run of the *same* plan, not sequential re-fires or distinct plans. *Severity unchanged at high; the dollar estimate is overstated for the current Haiku-default composition (`path-generator.ts:1791-1793` — old ultra→Sonnet upgrade removed unless `MODEL_COMPOSITION_LEGACY=1`), but the vector is model-independent.*
*Attack:* Delete activities between runs (or target a path with failing slots) to force a full re-generation each cycle at 10/min; uncapped over time. Per-user key also doesn't cap a botnet of accounts each at 10/min.
*Fix:* Consume a dedicated metered credit on regenerate/translate, or make `checkTokenBudget` include path tokens; tighten the limit for these specifically expensive routes.

**No global per-IP rate limit in middleware** — `src/middleware.ts:151-174`
The only global `/api` gate is an auth-token presence check; there is no per-IP request-rate ceiling anywhere in middleware (grep for rate-limit in middleware = 0 hits). Per-route limiters exist on only **40 of 196** routes. Self-hosted Coolify/Traefik provides no managed WAF, DDoS mitigation, or platform rate limiting. (*Finding's `notifications/route.ts` example does not exist; `dashboard/route.ts:15-40` running 7 parallel DB queries and `notebooks/route.ts:13-40` with nested includes are confirmed unthrottled.*)
*Attack:* One logged-in account scripts `GET /api/dashboard` or `GET /api/notebooks` at thousands of req/s from one IP → Postgres pool + CPU exhaust → app-wide outage that an edge-WAF deployment would absorb.
*Fix:* Add a coarse global per-IP token bucket in middleware via the existing Upstash limiter keyed on `clientIpFromHeaders`, returning 429 before the handler.

**Non-auth rate limiters fail OPEN when Redis is unset/unreachable** — `src/lib/rate-limit.ts:44-67`
`rateLimit()` defaults `failClosed=false`. `getRedis()` (`src/lib/redis.ts:8-12`) throws if `UPSTASH_REDIS_REST_URL`/`TOKEN` are absent, and `limiter.limit()` throws on a network error — both swallowed into the fail-open branch. All 9+ AI/import call sites pass only 3 args (verified: page-generate `:52`, ai-inline `:148`, essay-check `:115`, chat messages `:72`, path-create `:93`, code-execute `:127`, classify `:55`, youtube `:30`, doc-summarize `:48`). No UPSTASH entry exists in `.env.example` (concrete deploy-miss precedent per project history of missed Supabase env on Coolify). *Severity high, not critical: requires the Redis-unavailable precondition.* Auth limiters correctly pass `failClosed=true`.
*Attack:* On an Upstash outage or env miss, every AI rate limit returns `success=true`. Chat and PRO path generation (where `checkUsageLimit('ai_study_plan')` short-circuits `allowed=true` for PRO `-1`) lose their only burst control; bounded only by the non-atomic monthly token budget, which concurrent in-flight calls overshoot.
*Fix:* `failClosed=true` for AI/import limiters, or a startup assertion that refuses to boot without UPSTASH vars in prod; alert on the fail-open log; document the vars in `.env.example`.

### Medium

**PPTX/PDF export routes: no rate limit, no usage budget** — `app/api/export/pptx/route.ts:11-57` (+ export/pages/pdf, export/pages/pptx, export/pdf/split, flashcard-sets/[setId]/export-pdf, export-pptx, quiz-sets/[setId]/export-pdf, export-pptx)
*Verifier-corrected: severity high→medium, bankruptcyRisk true→false.* These are pure-JS in-process generators — `pptxgenjs` (`src/lib/pptx-generator.ts:1`) and `pdfkit` (`src/lib/pdf-generator.ts:1`) — so **no AI spend** and no headless-Chromium fork bomb; the impact is synchronous CPU + large Buffer allocation blocking the single Node event loop. The 500-slide cap (`:30-31,53-55`) bounds slide *count* only — there is no per-field content-length cap (unlike the page-export path's `.slice(0,2000)` at `pptx-generator.ts:264`), so one payload can carry 500 slides each holding megabytes of text. Auth is the only existing control.
*Attack:* One free account scripts large-payload exports in a loop → event-loop starvation / OOM → app-wide outage on the single Coolify container.
*Fix:* `rateLimit(rateLimitKey('export-pptx',request,userId),5-10,60_000)` on every export route; cap per-field content length.

**App-layer limiter fails OPEN removing the burst-throttle in front of every paid-AI and sandbox route** — `src/lib/rate-limit.ts:37-67`
*From the injection-ssrf dimension; severity medium.* The decisive case is `quiz/code-execute/route.ts:127`, which has **NO usage meter at all** (imports only `getAuthUserId`, `rateLimit`, `executeCode`) — the fail-open limiter is its sole abuse ceiling. AI routes retain Postgres-backed meters, so they're bounded; code-execute is not.
*Attack:* During an Upstash outage, an authenticated user loops `POST quiz/code-execute` → effectively unbounded Piston sandbox executions (each up to 8 tests × compile+run) → ~72,000 executions/hr saturating the sandbox + host.
*Fix:* `failClosed=true` on cost routes (code-execute especially, plus path-create, ai-chat, pdf/video import, essay-check); add a small DB-backed meter behind code-execute; health-alert on missing UPSTASH env.

**Synchronous file-import routes have no rate limit** — `app/api/notebooks/[id]/sections/[sectionId]/import/route.ts:19-55` (+ import-pptx, import-xlsx, flashcard-sets/import, append-pdf)
*Verifier-corrected: bankruptcyRisk true→false (zero AI/token spend — confirmed by grep across all five routes; pure local parse via mammoth `import/route.ts:64`, pdfjs `:69`, SheetJS).* The 50MB cap is client-declared only and depends on an out-of-repo Supabase bucket `fileSizeLimit`. `downloadFromStorage` (`storage.ts:130-140`) buffers the whole file with no cap.
*Attack:* An authenticated user repeatedly POSTs a 50MB highly-compressed DOCX/XLSX that expands to gigabytes → CPU/memory spike → OOM on the single container.
*Fix:* `rateLimit(rateLimitKey('file-import',request,userId),N,60_000)`; hard in-process size/row cap; run the heaviest parsers (xlsx) in a bounded worker.

**XLSX import → SheetJS with no rate limit and no pre-parse size/cell cap** — `app/api/notebooks/[id]/sections/[sectionId]/import-xlsx/route.ts:37-62`
*Verifier-corrected: bankruptcyRisk true→false (pure SheetJS parse + DB write, no LLM call); severity medium stands.* The route's *primary* parse (`XLSX.read` at `:47`, `sheet_to_json` at `:51`) runs on a fully uncapped buffer. A 25MB cap (`MAX_OOXML_BYTES`, `fileProcessing.ts:41`) exists but lives in `extractText()` — the *second* parse at `:59-62` — so it does not protect the first. `MAX_ROWS_PER_SHEET=500` (`contentConverter.ts:840`) is applied after the full in-memory expansion. xlsx is vendored SheetJS 0.20.3, flagged by the codebase's own comment (`fileProcessing.ts:31-39`) for known advisories.
*Attack:* Request a presigned token, PUT a crafted `.xlsx` directly to Storage (bypassing the JSON-body 50MB check), then loop `POST import-xlsx`. A workbook declaring a huge used-range / millions of sparse cells inflates to gigabytes inside `XLSX.read`/`sheet_to_json`, pinning CPU/RAM → OOM.
*Fix:* Add rate limit; hard pre-parse `buffer.length` cap before `XLSX.read`; bound rows×cols and abort early; set a concrete bucket `fileSizeLimit` and document it as load-bearing; parse in a worker thread with a wall-clock timeout.

**Mass account-creation abuse: per-IP cap but no CAPTCHA** — `src/lib/registration.ts:61-95`
Two per-IP controls fire on the credentials path (5 register/IP/hr fail-closed at `register/route.ts:17-24`; 3 accounts/IP/12mo at `:61-95`, also on the OAuth path at `oauth-user.ts:74-77`). But there's no CAPTCHA/PoW anywhere, and `enforceIpCap` fails open for `ip==='unknown'` (`:62-64`); the OAuth `signIn` path passes `ip='unknown'` when `headers()` throws (`config.ts:295-301`), leaving that signup wholly uncounted (`oauth-user.ts:98` guards `ip !== 'unknown'`). *The credentials path is gated by emailed 6-digit verification (per project memory), raising attack cost; the OAuth `unknown` path is environment-driven, not an attacker-toggled knob — severity medium stands.*
*Attack:* A residential-proxy/botnet pool mints thousands of free accounts (each ≤3/IP, ≤5/hr), each carrying a fresh 100k-token monthly quota, then drives AI generation fleet-wide. ~3,000–10,000 CHF/mo pure-loss COGS at scale, repeatable monthly.
*Fix:* Add CAPTCHA/PoW (Turnstile/hCaptcha) to credentials register + native OAuth create; require a verified provider email + best-effort risk signal before the OAuth `unknown` path creates; keep free per-account AI quota conservative.

### Low

**Non-atomic `checkUsageLimit→incrementUsage` (TOCTOU)** — `src/lib/usage-limits.ts:42-72`
*Verifier-corrected: high→low, bankruptcyRisk false.* The read-then-(deferred-)write race is real (check at `:42-50`, separate upsert at `:59-72`; increment lands after the LLM call), but the per-user Redis sliding-window limiters serialize bursts (5/min path-create, 10/min page-generate, 20/min chat), and the monthly token budget hard-caps total COGS. Residual overage is bounded to ~one rate-limit window. *Fix (hardening):* atomic reserve-then-settle (`UPDATE…SET count=count+amount WHERE count<limit RETURNING`); move increment before the LLM call.

**page-generate limiter keys on IP only, not user** — `app/api/notebooks/[id]/pages/[pageId]/generate/route.ts:50-55`
*Verifier-corrected: medium→low, bankruptcyRisk false (appears twice in the input — same finding from two dimensions).* The `generate:${ip}` key is the only AI route not using `rateLimitKey(prefix,request,userId)`. The XFF-spoofing premise is **refuted** under the default config: `clientIpFromHeaders` (`client-ip.ts:34-49`) indexes from the *right* of X-Forwarded-For with `TRUSTED_PROXY_HOPS=1`, so a prepended fake XFF is ignored. Residual: NAT'd users share one bucket; per-user `checkTokenBudget`/`checkUsageLimit` still cap cost. *Fix:* use `rateLimitKey('generate',request,userId)` for parity; verify `TRUSTED_PROXY_HOPS`.

**Video-import meters minutes non-atomically** — `app/api/notebooks/[id]/video-import/route.ts:195-238`
*Verifier-corrected: medium→low, bankruptcyRisk false (also surfaced from billing-integrity dimension at high→medium).* Real check-then-act race, but bounded by the cluster-wide 10/min Redis limiter × 60-min duration cap, and a per-job $0.50 cost ceiling (`gemini-ingest.ts:288-294`) aborts+refunds over-budget jobs before any Gemini call. Worst-case overshoot ~$1.11/window. *Fix:* atomic conditional reserve (`UPDATE…WHERE used+minutes<=limit`) before dispatch.

**Per-language daily translation budget checked non-atomically** — `app/api/community/paths/[shareId]/route.ts:654-674`
*Verifier-corrected: medium→low, bankruptcyRisk false.* The single-flight lock is keyed `(sharedPathId, language)` (`schema.prisma:1921`), so only *distinct paths into the same language* race the `$5/day/language` cap. Every translation consumes a scarce `path_translation` quota (FREE 5 lifetime, PRO 50/mo) plus 6/10min user + 12/10min IP caps — high friction for a few extra dollars. *Note:* the translation `rateLimit` calls (`:371,:386`) omit `failClosed`, so they fail open on a Redis outage (separate issue). *Fix:* reserve estimated cost atomically at lock-acquisition; add a global daily translation budget.

**Chat fires an extra unmetered Haiku intent-classifier call** — `src/lib/chat-stream.ts:316-332`
*Confirmed low, bankruptcyRisk false.* The classifier (`AI_CLASSIFIER_MODEL=claude-haiku-4-5`) only fires on *ambiguous generation-keyword* turns, not every turn — plain chat returns `'chat'` synchronously (`chat-intent.ts:78`), so it is **not** blanket per-turn overhead. The `scholar_chat` meter increments only after the main call, so an aborted ambiguous turn leaves the classifier call unmetered. ~$0.0015/call, 20/min capped. *Fix:* increment `scholar_chat` (or a pre-charge) before the classifier + main call; tighten the keyword heuristic.

**Monthly token budget is read-then-act (non-atomic)** — `src/lib/token-budget.ts:10-60`
*Verifier-corrected: medium→low, bankruptcyRisk false.* Real race, but overshoot is a finite one-window event per account per month (≤20 chat / ≤5 path calls, each `MAX_OUTPUT_TOKENS`-capped); the "compounds each minute" claim is wrong because the prior window's tokens are recorded by the next. *Fix:* reserve-and-settle / atomic compare-and-set, mirroring the atomic `failedLoginAttempts` pattern in `auth/config.ts`.

**No request-body size limit on App Router handlers** — `next.config.ts:44-109`
*Verifier-corrected: medium→low, bankruptcyRisk false.* No `bodySizeLimit`/`bodyParser` config, and route handlers buffer the full body via `request.json()` before any length check (essay-check `:130` precedes the cap at `:136`). **essay-check and doc-summarize have no per-feature usage meter** — `app/api/notebooks/[id]/essay-check/route.ts:115-179`
*Verifier-corrected: medium→low, bankruptcyRisk false.* Both rely on a 10/min rate limit + `checkTokenBudget` (which *is* effective for them — they write `ChatMessage.tokens`). *Two finding errors corrected:* doc-summarize's real path is `app/api/notebooks/[id]/documents/[docId]/summarize/route.ts` (not `documents/[docId]/…`), and neither runs Sonnet by default — essay resolves Haiku (`:168`) and doc-summarize resolves Gemini Flash-Lite (`:108`) unless `MODEL_COMPOSITION_LEGACY=1`. doc-summarize also short-circuits to a DB cache (`:79-86`). *Fix:* add `ai_essay_check`/`ai_summarize` FeatureTypes with FREE caps; lower the 50k-char essay / 400k-char summary input caps proportionally to tier.

**Presence-token HMAC verified with non-constant-time compare (aud ignored)** — `apps/web/ws-server.ts:72-89`
Confirmed low. `expected !== signatureB64` instead of `crypto.timingSafeEqual`; the issuing route stamps `aud:'presence'` (`presence-token/route.ts:23`) but `verifyPresenceToken` never checks it. Expiry *is* enforced (`:83`) and userId comes only from the verified payload. No billing/data-mutation authority; network timing attack infeasible against a 256-bit secret. *Fix:* use length-guarded `crypto.timingSafeEqual` (mirror `lemonsqueezy/webhook/route.ts:60-62`); enforce `payload.aud === 'presence'`.

**WS internal `/emit` shared-secret compared with non-constant-time equality** — `apps/web/ws-server.ts:222-231`

**Public-profile route returns voluntarily-public PII to any authenticated user** — `app/api/user/profile/[username]/route.ts:27-50` and `:105-135`
Confirmed low (two near-identical findings consolidated). Private profiles are correctly gated to minimal payload for non-friends (`:109-127`); no email/token/billing id/`birthDate` is exposed. **Admin authority is DB-derived and re-hydrated — confirmed NOT client-forgeable** — `src/lib/auth.ts:19-25`
Confirmed-safe control (no vuln). `getAdminUserId` reads `token.role` sourced from the DB (`hydrateTokenFromDb`, `config.ts:30-50`); all 12 admin routes gate on it; the most privileged write (`admin-background`) re-reads `role` off the DB (`uploads/signed-url/route.ts:308-313`). ## Per-dimension posture

- **AI cost-runaway & quota enforcement:** Weak. Every AI route is authenticated, but the cross-route "hard ceiling" is blind to all non-chat spend, meters are non-atomic and increment after the call, and several high-COGS routes (pdf-retry, publish, regenerate/translate) have no meter at all. This is the dimension with the live bankruptcy vectors.
- **Rate limiting, DoS & brute-force:** Mixed. Genuine Redis-backed limiter and a solid auth brute-force surface, but no global per-IP cap, fail-open on Redis outage, and unmetered export/file-import DoS lanes with no edge WAF behind them.
- **AuthZ / IDOR / RLS / multi-tenant isolation:** Strong app-layer discipline with zero current gaps, but resting on a single point of failure — RLS is entirely absent and Prisma runs as the privileged role, so one future forgotten check is full cross-tenant exposure.
- **Auth, session, secrets & billing webhooks:** Strong. No tier-escalation / free-PRO vector; HMAC-verified webhooks, hardened credential and native-OAuth flows, clean secret handling. Only two low-severity non-constant-time compares in the standalone WS server.
- **Injection, SSRF, file-bombs & RCE:** Good. Parameterized SQL throughout, textbook SSRF defenses, sandboxed code execution, hardened safe-math. Residual exposure is the unbounded SheetJS XLSX parse and the fail-open limiter.
- **Quota/meter integrity & user-data exposure:** Server-authoritative meters and well-scoped data endpoints (no PII/token leaks); the real risk is entirely on the cost side — path generation never counting toward the token budget and the universal non-atomic gate.
